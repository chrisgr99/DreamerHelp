# The help database: a maker's files, users' files, and a database that starts it off

A module's help comes from three places. A maker can ship help files inside their own plugin, written by hand or generated from marked comments in their source code. A user can write a help file for a module whose maker has not, in their own Rack user folder, and send it to DreamerHelp for the database. And DreamerHelp's own database, written by analysing each module's code, panel and manual, gives help to every module that can be analysed from the start. A card's text comes from the first of these that has it.

## Why

The text is data and it changes on a different clock from the code. It was compiled into DreamerHelp: a build step turned the database into `src/HelpText.cpp`, which was 9.7 MB of generated source, 109,000 lines, and a 16 MB object file inside a plugin whose own code goes weeks without a change. It is read from files now, and the plugin is a thirtieth of the size.

The people best placed to describe a module are the people who made it. A maker who ships help files with their plugin describes their module in their own words, keeps them current with their own releases, and needs nothing from DreamerHelp's repository: no pull request, no review, no wait for our release. DaveVenom proposed this on the VCV forum, and it is adopted as he described it.

Many makers will not write help, or not soon, and many of their modules are closed source. Users who know such a module well can write its help and share it, and the database is where shared help reaches everybody.

The database is what makes Help useful before anybody has written a file. It describes 4,193 modules by 377 makers, generated by analysis, and reviewed contributions from users are folded into it.

The database's source format also works against anyone reading it. A module's text is a flat list of lines, and separate tables say which parameter, input or output each line belongs to. To read the third knob's text you consult an index, take a line number and count down the list; to insert a line you renumber everything after it. Help files need a format where the text sits beside the control it describes.

## Where a card's text comes from

For each control, input, output and light, and for the module's description and notes, the first of these that has text for it:

1. **The maker's file**, in the `help` folder of the maker's installed plugin.
2. **A user's file**, in the Rack user folder.
3. **DreamerHelp's database.**

The maker's words win wherever the maker has written them; a user's words come before the database's, because a person who wrote them knew the module; and the database covers everything else. A file that describes only part of a module leaves the rest to the next source. A card says which source its text came from.

## The file format

JSON, one file per module. All three sources use it, so there is one reader and one set of rules.

**A plugin's help is a folder of module files, named by module slug, in all three places.** In the database it is `data/help/<PluginSlug>/`; in the user folder, `<user folder>/DreamerHelp/help/<PluginSlug>/`; in a maker's repository and installed plugin, the plugin's own `help/` folder, which needs no plugin name because the whole plugin is that plugin's. A set of files moves between them by copying the folder's contents.

The file holds the module's description, then its parameters, inputs, outputs and lights, then its notes. Each entry carries its own text and the identifiers it covers:

```json
{
  "plugin": "DreamerMPX",
  "module": "mpxPhrase",
  "description": "Places notes against the bars, chord changes and cadences of the chart on the cable.",
  "params": [
    { "ids": [0], "name": "Grid", "text": "The division the notes fall on." },
    { "ids": [1], "name": "Group", "text": "How long a breath group is, in seconds." }
  ],
  "inputs": [
    { "ids": [0], "name": "Chart in", "text": "Takes the chart." }
  ],
  "outputs": [
    { "ids": [0], "name": "Notes out", "text": "Carries the notes as an MPX stream." }
  ],
  "notes": ["There is no clock input."],
  "menu": ["Record: writes every note to a file."],
  "expects": { "inputs": { "0": "an MPX cable" } }
}
```

**`menu`** lists settings reached from the module's right-click menu, shown under a heading that says so. **`expects`** is a short phrase per jack, by number, shown under the jack's own text: what to send it, or what comes out.

**Sharing is a list of identifiers, not an index table.** One entry can cover several controls, which is how a row of sixteen step inputs shares one sentence, and the sharing is visible where it applies.

**`ids` are authoritative and `name` is advisory.** Rack identifies a control by its number, so that is what the file keys on. The name is there so the file can be read without the module in front of you; a card could later warn when it no longer matches the live name, which would mean a module rebuilt with its controls in a different order.

**Every field is optional except `plugin` and `module`.** A file can start with a description and a few controls and add the rest later; whatever it leaves out comes from the next source.

**An entry with empty text counts as left out**, so a file with blanks still to be written shows the next source's text for them, not nothing.

**`database` is a field the reader ignores.** An exported file puts the database's text there, beside an empty `text`, as a reference to write from; see Exporting a starting file.

The format is the one thing here other people depend on, so it is documented for makers and users on its own page, and it changes only in ways that keep existing files valid.

## The maker's files

One per module, inside the maker's own plugin:

```
<plugin folder>/help/<ModuleSlug>.json
```

They ship in the maker's plugin package like any other resource, through the library, and update when the plugin does. Nothing in DreamerHelp has to be released for them to appear, and they are never merged into the database.

A maker writes them in their own plugin's source repository, in its `help` folder, either by hand or by generating them from marked comments in the source (see Writing help in the source code). They build and install their plugin as they always do, which copies the files into the installed plugin folder, and the reload item shows the new text on the next card. The repository is the only copy anyone edits; the installed folder is replaced by the library on every update.

## Users' files

One per module, in the Rack user folder:

```
<user folder>/DreamerHelp/help/<PluginSlug>/<ModuleSlug>.json
```

The library never touches the user folder, so a user's file survives every update of both plugins. It is for a module whose maker has not written help, or has written too little: the user fills in what they know, and it shows on the card from then on.

**Sending one to the database.** A module's note — the one its title opens — has a Send this help link while a user's file for it is in use. It copies the file and opens a new issue on DreamerHelp's GitHub page with a form ready for it, where the user pastes it. That needs a GitHub account and nothing else. The submission is reviewed and folded into the database as analysis is: checked against the module, held to the style rules, and rewritten where it has to be.

**Once it has shipped**, the user's file only repeats the database, and it goes on standing in front of later improvements to it. A card that finds a user's entry identical to the database's should say so and offer to delete the file. Not built yet.

## Writing help in the source code

A maker can write each control's help in their source code, beside the line that defines the control's tooltip, and a tool we provide turns it into the maker's help files.

### Why beside the tooltip

A control's tooltip is defined in the module's setup code, on the line that configures the control: `configParam`, `configSwitch`, `configButton`, `configInput`, `configOutput`, `configLight`. That line names the control and gives its short name, its range and its units. The tooltip is best kept short; help is where the detail goes. So the help is written directly after that line, where a maker will look for it, and the two are read together.

### The markers

Each marker is a line comment beginning with `//?`. The question mark is the help badge's own symbol, the sequence does not otherwise occur in C++ source, and it survives any formatter.

| Marker | What follows it |
|---|---|
| `//?` | Help for the control configured on the line above. Further `//?` lines continue it. |
| `//?module` | The module's description. Further `//?` lines continue it. |
| `//?note` | One note about the module. Further `//?` lines continue it; each `//?note` starts a new one. |

An example:

```cpp
configParam(TEMPO_PARAM, 30.f, 300.f, 120.f, "Tempo", " BPM");
//? Sets the tempo when no clock is patched, 30 to 300 beats per minute.
//? With a clock patched, shows the tempo measured from the clock.

for (int i = 0; i < 8; i++)
	configInput(STEP_INPUTS + i, string::f("Step %d", i + 1));
//? Replaces the step's voltage while a cable is patched.

//?module Plays a chord chart as an MPX stream and as pitch voltages.
//?note A new module has no chart in it and plays nothing until a song is chosen.
```

The text is plain. Continuation lines are joined with a space, so help can be wrapped in the source to any width.

### The rules the tool follows

- **Help belongs to the configure call directly above it.** "Above" means after the whole call, since one call often runs over several lines of code.
- **Plain comments and blank lines** between the call and the `//?` lines are skipped. Any other code ends the search, so help can never attach to the wrong control.
- **The call names the control, and the tool turns the name into Rack's number** by reading the module's list of parameters, inputs, outputs or lights, counting a group declared as a run of several — Rack's `ENUMS(STEP_INPUTS, 8)` — as that many.
- **A call inside a loop** configures a run of controls: its first argument is the run's name plus a counter. Help written after it covers the whole run, as one entry naming every identifier in it.
- **`//?module` and `//?note` can be anywhere** in the source file that defines the module, and are usually at the top of it.
- **Anything it cannot place is reported**, with its file and line: a `//?` line with no configure call above it, or a call whose control it cannot resolve because a plugin configures its controls through helpers of its own. It never guesses.

### The tool

A script in DreamerHelp's repository, `tools/helpscan.py`, which a maker runs on their source files, by hand or as a step in their own build. It writes one file per module into the plugin's `help` folder, in the file format above. It needs Python and nothing else, and it reads source code only, so it runs anywhere the plugin builds.

## Exporting a starting file

DreamerHelp can export a plugin's help, one file per module, from the right-click menu. Each file lists every parameter, input, output and light the live module reports, with its name. Each entry's `text` is empty and its `database` field holds the database's text for it, or nothing where the database has none. So whoever starts from the export has the whole module laid out and the current text beside each entry to write from, and an entry they leave alone falls back to the database rather than freezing today's database text in front of tomorrow's.

The export asks for a folder. For a user it defaults to their help folder, `<user folder>/DreamerHelp/help/<PluginSlug>/`, where the files take effect as soon as they are filled in. A maker points it at the `help` folder of their repository.

## Reading the files

**A module's files are read when its card is first opened**, and kept. Nothing is read at startup: a card needs one module, and one small file costs less than drawing the card, where reading every file at launch would cost seconds.

**A menu item reloads**, so a change to any file shows on the next card.

**A parse error appears on the card**, with the file and the position, rather than the card silently falling back to the next source.

## Checking

`tools/validate.py` checks DreamerHelp's own database: the schema, the style rules, the line-length limit, the words that lean on something the reader cannot see. A user's submission meets those rules when it is folded in.

A maker's or a user's file is not held to our style rules while it is theirs. The module checks only what it needs to show it: that the file parses, that its identifiers exist on the module, and that its recorded names still match the live ones.

## Clarity keeps its snapshot

Clarity's port colouring is generated from DreamerHelp's database into `DreamerDevelopment/src/PortFamilies.cpp`, stamped with the DreamerHelp commit it came from. It stays that way. Reading the database at runtime would make Clarity's colours depend on DreamerHelp being installed, and a module that colours ports should colour them whether or not another plugin is present. Makers' and users' files do not affect port colours.

## How the database is kept

Two JSON files per module, both named for the plugin and the module.

**`data/help/<PluginSlug>/<ModuleSlug>.json` is the help**, in exactly the format a maker's or a user's file uses, and it ships. Nothing else is in it, so a maker who looks at what the database says about their module, or exports it as a starting point, sees only the help.

**`data/research/<PluginSlug>/<ModuleSlug>.json` is what the help was worked out from**, and it does not ship: each jack's family, which Clarity's port colours are generated from; the facts about what each jack expects, each with a citation saying where it was established; the writer's comments; lines no control is reached by; and where the module was read. `data/research/<PluginSlug>/.plugin.json` says where a plugin's entries were read, and carries the notice for a plugin whose figures could not be checked against a public source.

**The one thing the help file takes from the research is what each jack expects**, a short phrase derived from the facts and the jack's own line. `tools/build.py` keeps it in step; with `--check` it reports any help file that has fallen behind, which is the pull-request check. `tools/validate.py` checks both files: the schema, a citation for every fact, and the style rules on every line.

Building the plugin needs nothing but the Rack SDK.

**The migration.** The database was YAML, one file per plugin, compiled into `src/HelpText.cpp`. It was converted once into these two trees, and every module was compared, field by field, with the YAML it came from before anything was written. `tools/migration_check.py` then compared what the help files show with the last compiled table, for every module: description, notes, menu, the text of every input, output and parameter, and every "expects" phrase. All 4,193 modules matched.

## Not in this design

**Folding makers' files into the database.** A maker's files live with their plugin and are used from there.

**Reading help from tooltips.** A tooltip is kept short and help carries the detail, so the two are written separately; the source-code markers put them side by side.

**A separate distribution channel, or a packed format.** Makers' files and the database reach people inside plugin packages, through the library; users' files are written where they are used. All are read one module at a time.
